## Goal & Expected Outcome

Build **Wealth Master** — a single place to manage and see all personal finances: net worth,
cash accounts, investment portfolios, physical assets, liabilities and loans. It must run
across devices (laptop, phone, tablet), be hosted from GitHub, forecast investment and savings
growth, and calculate payback periods for loans.

"Done" for the overall programme is a working, self-hosted tool that replaces manual
spreadsheet reconciliation and answers three questions on demand:

1. What am I worth right now, and is it going up?
2. Where do I land in 5 / 10 / 20 years if I keep doing what I'm doing?
3. What is my debt actually costing me, and what changes if I pay it down faster?

The owner is Malaysian, based in Selangor; all currency, tax, and product context is Malaysian
(LHDN, PIDM, EPF, ASNB, flat-rate hire purchase). Working style: direct, output-oriented,
expects validated and tested components rather than drafts, and will flag stale or unverified data.

## Current State

Three planning documents are complete and reviewed (see Artifacts). A working prototype,
**Fund Desk v1**, exists as a single self-contained HTML file: it tracks Malaysian money market
funds, derives realised yield from monthly balance and income entries, and renders five
hand-rolled SVG charts with zero external requests. It was validated headlessly with jsdom
across twelve edge cases (single-fund donut, funds with no entries, negative income, RM 9.5m
balances, corrupt localStorage, quota-exceeded saves, malformed imports, HTML injection) — all
clean, no console errors, export/import round-trip intact.

Fund Desk v1 is browser-local only, funds-only, and cannot forecast. It is the migration source
for Wealth Master, not the foundation — its store, chart engine, and test harness are worth
porting; its schema is not.

Nothing has been built for Wealth Master itself yet. No repo exists.

## Key Decisions

- **Wealth Master inverts the Warrant Desk data flow.** Warrant Desk is one-way (GitHub Actions
  writes market data to a Sheet, the app reads). Wealth Master's user is the data source and must
  write from a phone, so the Sheet becomes a read-write system of record with the browser as
  client. This makes sync, not features, the hard part of the build.
- **Google Sheet as system of record, localStorage as offline cache.** No backend server, no
  recurring cost, and the Sheet stays human-readable and hand-editable as a fallback entry path.
- **Google OAuth (Identity Services) with `drive.file` scope, not a service account.** A service
  account key cannot ship to a browser. `drive.file` limits the app to the spreadsheet it created.
  Access tokens stay in memory, never localStorage.
- **Public repo is acceptable and is the default plan.** Code goes public on GitHub Pages; data
  lives only in the owner's own Drive and browsers. This avoids needing a paid GitHub plan for
  private Pages, but must be enforced by design — no data files in git, ever.
- **Flat-rate and reducing-balance loan maths are separate engines, not one parameterised path.**
  Malaysian hire purchase is flat-rate with Rule of 78 early settlement — genuinely different
  maths. A single code path with a flag will be quietly wrong for years.
- **localStorage is a cache, not durable storage.** iOS Safari evicts it after roughly 7 days
  idle. The Sheet is the durability guarantee.
- **Conflict resolution is last-write-wins on `updatedAt`, with the losing version retained in a
  conflict log.** Deletes are tombstones, never hard row removal.
- **Charts are hand-rolled SVG, no charting library.** Proven in Fund Desk v1; keeps the app fully
  offline and dependency-free.
- **Scope boundaries are firm.** No budgeting or expense categorisation (Receipts Tracker owns
  that), no trade signals (Warrant Desk owns that), no bank aggregation or scraping, no multi-user.

## Notes for Continuation

- **Build P0 before anything visible.** The pull toward building the net worth chart first will
  be strong. A chart on a lossy store is worse than no chart — it is confidently wrong. This was
  a deliberate, settled decision; do not re-litigate it.
- **Validate loan maths against real statements before building any chart on top.** Both the
  reducing-balance and flat-rate engines must reconcile to the sen against an actual bank and an
  actual hire purchase statement. This is the highest-consequence risk in the programme.
- **Test headlessly, do not eyeball.** Fund Desk v1 used jsdom to drive the real DOM and assert
  on rendered output, storage round-trips, migrations, and injection safety. Carry this forward
  and run it as a CI gate, matching the Warrant Desk repo pattern.
- **Watch for false positives in output scanning.** A Fund Desk v1 test flagged "NaN" in the
  rendered page; it was scanning `body.innerHTML`, which includes inline `<script>` source where
  `isNaN()` guards legitimately appear. Scan only rendered containers with script tags stripped.
- **Fail visibly.** Following the Warrant Desk convention, a broken data source writes an error
  row rather than aborting the run, so failures are obvious the same day.
- **Add a CI gate that scans for financial data in commits** before the repo goes public. Once
  something is in git history it is effectively permanent.
- Reference data from the pipeline is advisory only and must never overwrite a user-entered
  valuation.
- Forecasts must always show their assumptions on screen and present a scenario range, never a
  single confident number.

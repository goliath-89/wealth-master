## Goal & Expected Outcome

Build **Wealth Master** — one place to manage and see all personal finances: net worth,
cash, investments, physical assets, liabilities and loans. Runs across laptop, phone and
tablet, hosted from GitHub, forecasts growth, and models loan payoff.

It answers three questions on demand:

1. What am I worth right now, and is it going up?
2. Where do I land in 5 / 10 / 20 years if I keep doing what I'm doing?
3. What is my debt actually costing me, and what changes if I pay it down faster?

**All three are now answered by working software.** The owner is Malaysian, based in
Selangor; all currency, tax and product context is Malaysian (LHDN, PIDM, EPF, ASNB,
flat-rate hire purchase).

## Key Decisions

Recorded here because several look reversible and are not.

### ADR 001 — file store, not Google Sheets (`docs/decisions/001-...md`)

The original architecture made a Google Sheet the system of record with an offline queue
and last-write-wins conflict resolution — roughly two of three P0 sessions. The owner
pushed back on the setup burden. Re-examination found **only one of six usage scenarios
uses the phone, and it reads**; and valuations are monthly, so a monthly-refreshed file is
not stale.

The store is now a JSON file in a synced folder, held open via the File System Access API.
Multi-device safety is a **single-writer model with a blocking stale-import warning**, not
a merge engine. `updatedAt`, `deviceId` and tombstones stay in the schema so Sheets sync
could return later as a second adapter without a migration.

**Revisit if** phone entry becomes routine, or two devices are regularly edited between
syncs.

### The two loan engines never merge

Malaysian flat-rate hire purchase is different arithmetic from reducing balance, not a
variant. Risk **R4** — implementing flat as reducing — is the highest-consequence risk in
the programme because it is quietly wrong rather than visibly broken. Consequences
enforced in code and tests:

- A test asserts the flat engine charges **identical interest every month**. If it ever
  varies, flat has silently become reducing.
- Extra payments **do nothing** to a flat facility. `flatSchedule` ignores them, and a test
  asserts extras change no row. The only lever is early settlement under **Rule of 78**
  (`rebate = charges × r(r+1)/n(n+1)`), verified by hand.
- The overpay-vs-invest panel gives flat loans **no overpay branch at all**, whatever the
  assumed return.
- Multi-debt avalanche ranks by **effective** rate: 3.4% flat is really ~6.3%, so a quoted
  ranking would pay it off last when it should be near first.

### Blank is not zero

A skipped account has an unknown balance, not RM 0. Fund Desk v1 used `parseFloat(x) || 0`,
which would quietly wipe a forgotten account from net worth. Blank stores `null`; a typed
zero stores `0`; tests assert the two stay distinguishable end to end.

The one deliberate exception is **savings rate**, where a month with no contribution counts
as a month at zero — a month you did not save in is still a month, and excluding it would
flatter the rate.

### Carry forward, but mark it

An unrecorded month keeps the last known balance rather than vanishing, and every carried
figure is marked three ways: an asterisk on the figure, a hollow point on the chart, and a
sentence naming what is stale and which month it came from. Staleness travels **out of the
calculation** attached to each number, so the UI cannot lose it.

### Forecasts are ranges, never a number

R3 is enforced in the engine, not the UI: there is no single-scenario entry point. The
headline is "in 10 years, between RM X and RM Y" with the spread shown. Assumptions travel
with every projection.

### The engine is measured, never tuned

Statement figures are stored as the owner's data and compared against the schedule.
Entering one changes no calculation, and a test asserts `reconcile()` does not mutate the
schedule it is handed. **Never adjust a formula to match one statement** — that is
hardcoding by another name and would break every other loan silently.

### Volatile figures are editable defaults, never facts

Tax relief limits, scenario growth rates and PIDM thresholds change. All are editable and
labelled as needing confirmation. Apply the same rule to EPF account splits when P4.5 is
built.

### Money is integers

All loan arithmetic is in sen. Rounding a float 360 times drifts visibly, and a schedule
that does not reconcile to the sen fails AC-2/AC-3 by definition.

## Open Items / Blockers

### 1. Loan engines are only partially verified

`docs/loan-validation.md` says **PARTIALLY VERIFIED**. The engines pass worked examples but
have not been checked against a real statement. The owner does not have statements
itemising monthly interest.

**The obtainable check is the monthly instalment**, which depends on principal, rate,
tenure and basis simultaneously — a match confirms all four, and a wrong basis produces a
visibly different figure. Enter it under **Check against a statement** when editing a loan.
Loans read *Unverified* until then.

What an instalment match cannot settle is **monthly rest vs daily rest**. The reducing
engine computes monthly rest; most Malaysian housing loans are daily rest, where interest
depends on the exact day a payment lands. Expect a small, month-length-dependent
difference. Flat-rate HP has no such ambiguity.

### 2. The repository is public

Code and specs only, by design (SEC-8). No financial data has ever been committed; CI
scans every push. `docs/` is public, including the requirements and this handoff — all
strategy and method, no figures.

### 3. Pages deploys on push

Any commit to `main` publishes. Tests gate the deploy, but there is no staging step.

## Notes for Continuation

**Working style.** Brief, work-first replies: ship the increment, run the tests, verify in
a real browser, commit and push, then report in a few lines. Reasoning belongs in code
comments and commit messages. **"LFG" means proceed** — act, do not ask.

**Verify in a real browser, not only jsdom.** jsdom does no layout and does not enforce
CSP, so it silently passed a 24px `input[type=month]` and would have passed a broken CSP.
Two caveats learned the hard way: the browser pane reports `documentHasFocus: false`, so
`element.blur()` fires no event — dispatch real `FocusEvent`s instead; and clearing
localStorage without reloading leaves stale in-memory state that looks like a duplicate-write
bug.

**Bugs the tests caught, as evidence the harness earns its keep.** `upsertValuation` silently
dropped `units`/`unitPrice`, making unit-based holdings unrecordable. Seeding default
scenarios during render created records the owner never made, so every cross-device import
falsely warned it would discard three scenarios. `removeRecord` chose its error box from a
hardcoded ternary, so a refused liability delete wrote its reason into the holdings box —
invisible, making the button look inert. The multi-debt simulation did not mirror the
engine's final-instalment adjustment and reported debt-free a month late. **Rendering must
never mutate state** — that rule came out of the second one.

**Every new entity needs five things:** a factory in `schema.js`, an entry in
`ENTITY_LISTS`, a migration step, CSV columns in `csv.js`, and registration in
`tests/helpers.js` (both `loadLib` and `loadApp`). Miss the last and every UI test fails
confusingly.

**Escape everything user-typed.** SEC-7 has a test per surface: a name of
`<img src=x onerror=...>` must create no element and run nothing.

**Do not re-litigate settled decisions.** The two loan engines stay separate. Blank stays
distinct from zero. Forecasts stay ranges. Statement figures never tune a formula.
